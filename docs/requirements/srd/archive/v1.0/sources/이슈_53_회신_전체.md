### MC-002 — 고정 관측 자세 호모그래피와 이동 카메라 추종

**G0 범위 수정 요청.** G0부터 로봇/카메라 이동 중에도 유효한 박스 베이스 좌표를 갱신하는 방향입니다. 고정 관측 호모그래피는 초기 위치 획득에 사용하고, 이동 중 변환은 촬영 시각 pose·핸드아이·박스 윗면 평면을 반영해 비전이 제공해 주세요.

“G0는 초기 위치만 확정, 이동 중 갱신은 B”라는 단계 구분은 이 방향에 맞춰 수정해 주세요. 정적 H를 이동 중에도 유효하다고 취급하지 않으며, 관측 누락 때의 예측 허용 범위·종료 조건은 실측 후 정합니다. 동적 변환·촬영/pose 정합이 검증되기 전에는 해당 G0 항목을 통과로 표시하지 않습니다.

1920×1080 캘리브레이션 원본과 1280×720 운용안의 픽셀/camera_info 정합도 필요합니다. 하류 기준점·상류 외삽·리치를 구분하고 학민님의 하류 진입 후 첫 접근 제안은 검증 구간을 맞춘 뒤 확정해 주세요.

### MC-004 — 촬영·pose·제어 시각과 시계 이력

**시각 의미 확인, 수신 시각 사용은 검증 조건부.** 중요한 것은 촬영한 영상과 변환에 쓰는 pose가 허용 시간 오차 안에서 같은 물리 시점을 나타내는 것입니다. 실제 pose 측정 시각을 우선하며, 제공할 수 없다면 stamp를 조회 응답 수신 시각으로 명시하고 RTT·큐 지연·불확실성을 기록해 주세요. 수신 시각이나 RTT/2를 실제 측정 시각/보장된 오차로 단정하지 않습니다.

공통 시계, 카메라 stamp의 시계 원천, pose 이력/보간 범위와 동적 좌표 오차를 확인하겠습니다. 제안된 50ms 보간 간격·1초 이력·약50Hz pose 주기는 검증 대상입니다. 시점 정합 허용치와 capture→servo 소비 지연은 별개이며, age=100ms를 자동 정지 기준으로 채택하지 않습니다.

### MC-006 — 픽업 phase·성공 인계·reason enum

**단계·인계 의미 확인, 높이/파지 방향 미확정.** phase는 PREPARE/TRACK/DESCEND/GRASP/LIFT/VERIFY 방향으로, reason은 대문자로 맞춥니다. reason 전체 허용값·취소 CANCELED·ROS action status의 대응은 문서에서 확인하겠습니다. err_u/v의 px 의미는 유지하며 제어의 m 오차와 섞지 않습니다.

grasped=true는 물체 확보 후 안전 높이까지 LIFT·VERIFY를 마친 픽업 성공 인계입니다. 닫힘 완료만으로 manager에 인계하지 않습니다. 학민님 새 회신의 31mm 면 파지는 BRD의 46mm 면/닫힘축 가정과 다릅니다. 최종 파지 방향과 인계 높이는 아직 정하지 않았으며, 기존 벨트 방향 ±22mm 여유를 그대로 적용하지 않습니다. 방향 변경 시 폭·힘 재시험, 높이 확정 시 플랜지/TCP 기준과 간섭을 함께 확인해야 합니다.

### MC-008 — 10/10 게이트와 개루프 검토 조건

**폐루프 FF+P 우선 및 자동 전환 금지 방향 확인.** 10/10의 20사례·14/20(70%) 성능 점검은 유지합니다. 날짜 도달이나 목표 미달만으로 개루프로 자동 전환하지 않고, 로그·원인·개선 결과를 근거로 팀이 대안을 판단합니다.

현지님의 게이트 회의/ADR-0002 정정 방향에 동의합니다. 범위 조정·개루프 대안·일정 연장은 회의에서 판단할 후보이며 지금 채택한 결과는 아닙니다. speedl 지원 여부의 실행 경로 문제와 폐루프 성능 판단은 구분해 기록합니다.

### MC-009 — 단일 설정 snapshot·스키마·단위·유효값

**동일 설정 snapshot 방향 확인.** 초기 버전은 launch가 동일 공유 설정을 관련 노드 파라미터로 전달하고 version/hash로 일치 여부를 확인합니다. 공유 writer는 manager, servo 전용 값은 병후 파라미터로 구분합니다. 공유 설정 변경은 정지 상태에서 동일 버전을 재적용하고 준비 확인 후 재개합니다.

### MC-010 — 플랜지/TCP·orientation·좌표 원점

### MC-011 — speedl/servol/move_line 실제 API·큐·주기

### MC-013 — 닫힘 중 추종과 비차단 실행·busy 의미

**닫힘 대기 중 추종 지속을 확인합니다.** servo는 Gripper를 비동기로 요청하고, 그리퍼가 닫히는 동안에도 추종 목표 계산·servo_cmd 발행을 계속합니다. 유효한 파지 성공 또는 실제 파지 완료 피드백을 받은 뒤 파지 판정에 따라 추종을 끝내고 LIFT로 전환합니다. 이후 VERIFY/안전 높이 확인 뒤 manager에 인계합니다.

### MC-014 — cancel·watchdog·실제 정지 확인

**기본 정지 방향은 잠정 확인, A/G0 최소로 우선 정합합니다.** stop/cancel 때 신규 작업·새 servo 목표를 차단하고 gateway 우선 정지를 요청합니다. 실제 정지 확인 뒤 action 취소를 완료하며, 확인 불가면 PAUSED·새 goal 금지입니다. 단발0속도나 pose 불변만으로 정지를 확정하지 않으며, 보유 물체 자동 개방은 금지합니다.

### MC-016 — 적재 완료·결과 발행·복귀·DB 순서

## 박병후 추가 확인 — TCP 명령·파지 판정·기본 정지 처리

[학민님 후속 회신](https://github.com/yujh5537/rokey_cobot2_VOSS/issues/53#issuecomment-6016090699)을 확인했습니다. 이동 중 유효 좌표의 G0 포함, pose 수신 시각·RTT 불확실성 기록, 동일 설정 snapshot, 폐루프 우선·자동 전환 금지, 최신 명령·자원별 실행, 시험 분모 및 100ms 성능/운전 기준 분리 등 수용해 주신 방향을 확인합니다.

추가 선택이 필요했던 세 가지는 아래처럼 결정합니다. **정지 처리는 초기 운영에 맞게 단순화합니다.** 이전 병후 댓글의 정지 관련 상세는 이번 회신으로 보완하며, 별도 STOP_UNCONFIRMED reason·자동 정지 판별 기능을 초기 필수로 추가하지 않습니다.

### MC-010 — 실제 TCP 기준 속도 명령 채택

- `/voss/robot/pose`는 실제 TCP pose, `servo_cmd(TwistStamped)`는 **TCP 기준점의 속도를 `base_link` 축으로 표현**합니다. ROS 단위는 선속도 m/s·각속도 rad/s입니다.
- 원본 voss_config의 플랜지 좌표는 유지하고, 등록 툴·오프셋·장비 단위/자세 변환은 gateway가 담당합니다. 회전이 있으면 TCP 선속도가 servo의 명령값과 맞도록 처리합니다.
- **G0 추종은 고정 파지 자세·각속도 0으로 시작**합니다. 회전 제어가 필요해지면 설치 API 의미와 툴 변환을 검증한 뒤 사용합니다.
- T32에서 실제 TCP 및 베이스 원점·축, 등록 툴과 설정의 일치를 확인하는 계획을 유지합니다.

### MC-012/013 — 완료·감지·보고폭으로 LIFT 진입 판정

**유효한 통신의 닫힘 완료 응답 + grip_detected + 검증된 보고폭 범위**를 함께 확인해 servo가 물체 확보를 판정합니다.

그리퍼가 닫히는 동안에는 추종 계산·명령 발행을 계속합니다. 위 조건으로 확보를 판정한 뒤 추종을 끝내고 LIFT로 전환하며, LIFT/VERIFY에서 보유 유지·안전 높이를 확인한 뒤 `grasped=true`로 인계합니다. 닫힘 완료만으로 빈 파지를 성공으로 처리하지 않습니다.

`width_actual`은 RG2 **보고폭**으로 명시하고 목표폭과 구분해 주세요. 39mm·14N·39.5~41.5mm는 31mm 면의 현재 시험 후보이며 최종값으로 확정하지 않습니다. T34의 무손상·빈 파지·미끄러짐·LIFT 유지 결과와 최종 방향에 따라 폭·힘을 설정합니다. `OK/TIMEOUT/INVALID/BUSY/COMM_ERROR` 응답 의미는 제안하신 구분으로 문서에 정리하는 방향을 확인합니다.

로봇/RG2 자원 분리·비차단 호출·중복 자원 차단은 유지합니다. 요청 `attempt` 필드는 우선 추가하지 않고, servo가 **goal/attempt별 future 문맥**을 관리해 이전 요청의 늦은 응답을 배제하는 안으로 진행하겠습니다. 늦은 응답을 무시하는 것과 gateway에서 진행 중인 동작의 종료·자원 해제를 확인하는 것은 각각 처리합니다.

### MC-006/014 — 정지 요청 오류는 일반 실패와 로그로 처리

초기 구현은 다음 흐름으로 맞춥니다.

1. stop/cancel 시 신규 작업과 추종 명령 발행을 차단하고 gateway에 정지를 요청합니다.
2. gateway의 정지 처리가 정상 완료되면 action을 `CANCELED`, reason을 `CANCELED`로 종료합니다.
3. 정지 요청에 응답이 없거나 오류가 나면 정상 취소 완료로 처리하지 않습니다. action은 실패(`ABORTED`), reason은 기존 `DEVICE_ERROR`를 사용하고, **“정지 요청 응답 없음/오류”와 해당 요청을 로그에 남깁니다.** manager는 PAUSED로 두고 자동으로 다음 작업을 시작하지 않습니다. 사람이 현장에서 로봇 상태를 확인한 뒤 수동 재개합니다.

응답이 없다는 것은 로봇이 실제로 멈추지 않았다는 뜻이 아니라, 프로그램이 정지 처리 결과를 확인하지 못했다는 뜻입니다. 초기에는 사람이 눈으로 확인하는 운용을 사용하며, 새로운 자동 정지 판별 기능이나 별도 `STOP_UNCONFIRMED` enum을 만들지 않습니다. PR #65의 reason 후보와 이전 상세 제안은 이 최소안에 맞춰 주세요.

실패 result의 `grasped=false`는 성공 인계가 완료되지 않았다는 의미이며, 빈손이라고 간주해 보유 물체를 자동 개방하지 않습니다. 기본 stop/cancel은 MC-014의 A/B 중 기본 정지 범위이며, 단계별 자동 resume·재기동 복구는 MC-015 B 후속으로 둡니다. watchdog200ms·최대 정지 지연/거리 등은 기존 실측 계획으로 확인하고, **관측 지연100ms 초과 자체로 중단하지 않는 결정**은 유지합니다.

### 남은 실측·다른 담당자 정합

- **MC-006/012 파지 방향·인계 높이:** 두 방향의 동일 조건 T34 결과 후 방향을 정하고, TCP/플랜지 기준·박스/핑거의 벨트 이격·간섭을 함께 확인해 인계 높이를 정합니다. 31mm 면 최종 채택이나 기존 ±22mm 벨트 방향 여유를 가정하지 않습니다.
- **MC-011 실행 경로:** 실제 stream 지원·단위·적용 proxy·backlog·pose RTT·정지 우선성은 T32 증거로 확인합니다. 소스 확인과 실제 동작을 구분합니다.
- **MC-016:** 적재 후 복귀 실패에서 `RETURN_FAILED + placed_stamp 유지`로 적재와 복귀 오류를 분리하는 방향을 권고합니다. 최종 업무 결과/중복 방지 계약은 현지님과 맞춰 주세요. 응답 유실은 상태 확인 없이 자동 재호출하지 않으며, `placed_stamp`는 개방 완료 proxy로 실제 적재와 대조합니다. `BUSY→READY`를 관측 자세 도달 시각으로 쓸 때에는 실제 도달 조건과 사건 출처가 문서·구현에 정의돼야 합니다. servo는 픽업 인계와 측정 증거 연결을 담당합니다.
