# ADR-0007: 송장 OCR 은 PaddleOCR(한국어) + 방향 고정 크롭 + 자모 편집거리 매칭

- 날짜: 2026-10-07
- 상태: 제안됨 (T18 결과로 결정 담당 남현지 제안, 리뷰 후 승인)
- 결정자: 남현지 (비전·OCR)
- 관련: T18(#27), TR-OCR-03·04·05, NFR-02, BRD 3.2(분류코드 규칙)

## 배경
- 송장 40×25 mm, 분류코드 5.5 mm·동 이름 4.5 mm. 관측 자세(1920×1080)에서 송장이 약 106×172 px, 분류코드 글자 높이 약 23 px 로 작다.
- 송장은 박스 윗면에 늘 같은 방향이지만 벨트 위 박스는 ±40° 까지 돌아간다(10/06 정지 50장 중 6장).
- 흐린 송장은 동 이름이 한 자모씩 틀린다(역삼동 → 역심동·역상동).

## 결정
1. **엔진: PaddleOCR 3.x(PP-OCRv5) `lang="korean"` 로컬.** 분류코드·동 이름을 한 번에 읽는다(TR-OCR-04).
2. **전처리(TR-OCR-03):** 송장 회전 사각형 → 긴 축 두 방향 중 "관측 자세에서 글자가 나아가는 방향"(`BASELINE_DIR`, 화면 아래)에 가까운 쪽을 글자 방향으로 골라 원근 보정 + 3배 확대. 방향 고정 지식을 쓰되 ±90° 안 회전은 모두 바로 선다. 대비 강화(CLAHE)는 옵션, 기본 끔(10/06 데이터에서 필요 없었음).
3. **매칭(TR-OCR-05, `voss_vision.label_match`):** 분류코드는 접두 S 를 무시하고 숫자 4자리의 끝 두 자리(동 번호)를 맞춘다. 동 이름·별칭은 **자모 편집거리**(삼→심 = 1/9)로 맞추고 유사도 0.6 미만은 버린다. 코드·동이 같은 후보 → AGREE(1−(1−sc)(1−sd)), 다르면 코드를 따르되 ×0.5(재확인행), 코드만 ×0.8, 동만 ×0.7. 2위 후보는 `dong_alt` 로 질문에 쓴다(TR-OCR-07). 가중치는 제안값.
4. **VLM 폴백(TR-OCR-04 2차 확인)은 지금 넣지 않는다.** 정지 50장에서 저신뢰가 0건이라 쓸 곳이 없고, API 지연·비용·오프라인 시연 위험이 있다. 2단계(추종 중, T19) 저신뢰 비율을 보고 다시 판단한다.

## 결과 (T18, 10/06 정지 송장 50장, 개인 PC CPU)
- 분류코드 정확도 **50/50 = 100%** (흐린 송장 제외 45/45, 흐린 송장 5/5). 자동 확정(신뢰도 ≥ 0.6) 중 오답 0. 50장 모두 AGREE.
- 개발 중 1장(S0703_15, 약 40° 회전)이 "고정 90° 회전" 방식에서 실패해 2번 방식으로 바꿨다. 같은 50장으로 다시 잰 값이므로, 10/07 정식 송장 세트(T33)로 한 번 더 확인한다.
- 흐린 송장 번짐이 약해 재확인 → 질문 경로는 이 데이터로 시험되지 않았다(pending #10, T33 에서 더 흐리게).
- 지연: CPU 에서 한 장 약 1.6 s(참고). TR-OCR-01(1단계 300 ms)은 공용 PC GPU 에서 잰다.

## 고려한 대안
- Tesseract(kor): 한글·작은 글자 정확도가 낮고 회전에 약하다.
- EasyOCR(ko): 정확도는 비슷할 수 있으나 PyTorch 의존이 커서 비전 컨테이너가 무거워지고 GPU 메모리를 Whisper 와 더 나눠 쓴다. PaddleOCR 가 기준을 넘어 비교를 미뤘다.
- 음절 편집거리: 흐린 오독(삼→심)이 1/3 로 멀게 나와 임계를 낮춰야 하고, 그러면 받는 사람 이름과 섞일 위험이 커진다.
